## 1. How to run it, and which ports to open

**Open no new ports on the EC2 security group.** Every service on the box binds to 127.0.0.1, so it cannot be reached
from the internet. From your laptop, use an SSH tunnel:

```bash
ssh -L 8080:127.0.0.1:8080 -L 5000:127.0.0.1:5000 -L 8081:127.0.0.1:8081 ubuntu@<this box>
```

| Local port | What | Notes |
|---|---|---|
| 8080 | **the app** (nginx + SPA, `/api` proxied): open http://localhost:8080 | Docker Compose stack |
| 5000 | moto (local S3) | the browser POSTs uploads here, so tunnel it too, or uploads fail |
| 8000 | API directly (`/api/health`) | optional |
| 15672 | RabbitMQ management UI (dev credentials in `deploy/compose.dev.yml`) | optional |
| 8081 | the Helm chart on k3d, through Traefik | sample analysis only; uploads go to an in-cluster moto that the browser cannot reach |

For production later (Phase 7), the EC2 security group opens only **22 (your IP), 80 and 443**, never 6443.

**Commands** (from the repo root; the toolchain is already installed on this box):

```bash
make dev                     # build + start postgres, rabbitmq, moto, migrate, api, worker, web
make dev-down                # stop it (keeps the database volume)
make test                    # abkit + backend + frontend tests (needs `make dev` or `make infra-up`)
make test-integration        # real RabbitMQ + Celery worker + API end to end
make lint                    # ruff, tsc, eslint, helm lint, kubeconform
make k3d-up k3d-deploy k3d-smoke   # the Helm chart on a local k3s 1.36 cluster
make results-abkit results-tests   # regenerate results/*.json
make bullets                 # resume bullets from results/ (deploy number stays MISSING until Phase 7)
make help                    # everything else
```

On a fresh machine: `make python` first (installs CPython 3.12.16 for uv; DECISIONS.md D1), then `cd frontend && npm ci`.
State left running on this box: the Compose stack and the k3d cluster `ea`. Stop them with `make dev-down` and
`make k3d-down` when you are done.

## 5. Plain-English walkthrough (for interviews)

### What it does, in one breath
You give it an A/B test file, or click the sample. It answers four questions: did the change win and by how much (with a
95% confidence interval); was the traffic split healthy (sample ratio mismatch); did the test have enough data to
notice a meaningful effect (power and minimum detectable effect); and did variance reduction (CUPED) help. The answers
come as one plain sentence plus charts, and every result has a shareable link that always shows the same numbers.

### The request flow (follow one upload)
1. **The browser asks the API for permission to upload** (`POST /api/uploads` with name and size). The API checks the
   name ends in `.csv` (415 if not) and the size is ≤ 50 MB (413 if not), creates an `Upload` row, and returns a
   **presigned POST**: an S3 URL plus signed form fields. The signed policy says "only this exact key, only 1 byte to
   50 MB". (`backend/analyzer/views.py: UploadCreateView`, `storage.py: presigned_post`)
2. **The browser sends the file straight to S3** with XMLHttpRequest, which is what drives the progress bar. The API never
   touches the bytes, so a slow 50 MB upload cannot tie up a gunicorn worker. (`frontend/src/api/upload.ts`)
3. **`POST /uploads/{id}/complete`:** the API checks the object exists (HEAD: 409 if missing; 413 if too big), reads
   only the first 256 KB (a ranged GET), parses the header and 20 rows, and returns them for the preview.
   (`preview.py`: drops a half-read last line so a cut UTF-8 character cannot cause a false 422.)
4. **The user maps columns** (variant, control label, metric, binary or continuous, optional pre-period and planned
   split, alpha) in a React Hook Form + Zod form that guesses sensible defaults from the preview.
5. **`POST /api/analyses`** validates the mapping against the header (422 otherwise), saves an `Analysis` row as
   QUEUED, and *after the database commit* sends a Celery message to RabbitMQ. It returns **202** in milliseconds.
   (`transaction.on_commit`, so the worker can never receive an id before the row exists.)
6. **The page polls** `GET /api/analyses/{id}` every second (TanStack Query `refetchInterval`) and stops once the status
   is SUCCEEDED or FAILED.
7. **The Celery worker** (`tasks.py: run_analysis`): marks RUNNING; streams the S3 object to a temp file while computing
   its sha256; checks whether an identical analysis (same file hash, same mapping hash, same abkit version) already
   succeeded and, if so, points at it (`reused_from`) and stops; otherwise **DuckDB** reads the CSV (every column declared
   as text, then `TRY_CAST`, counting dropped rows by reason) and hands one numpy array per arm to **abkit**, which
   returns the result JSON and the verdict sentence. The result is saved and the status becomes SUCCEEDED.

### The statistics (`abkit/`)
- **Effect and CI:** Welch's t-test on the difference in means, which does not assume equal variances. For a 0/1 metric
  the mean is the conversion rate, and with tens of thousands of rows per arm the t interval equals the usual normal
  interval for a difference in proportions. Binary effects are reported in percentage points.
- **Several treatments:** each is compared with control, and p-values are Holm-adjusted so the chance of *any* false
  positive stays at alpha.
- **SRM:** a chi-square test of the arm sizes against the planned split. Flagged below p = 0.001, because a real
  mismatch means the assignment or logging is broken. When it fires, the verdict starts with "Do not trust this result".
- **Power/MDE:** the smallest true lift the test would detect 80% of the time. When a result shows "no detectable
  difference", the MDE says whether the test could have seen an effect worth caring about.
- **CUPED:** subtract the part of the metric that a pre-experiment value predicts (theta = cov/var); the variance removed
  equals the squared correlation. On Hillstrom the correlation with prior spend is about 0.07, so only about 0.4% of the
  variance goes away: "not helpful here".
- **How it is verified:** the same formulas as the lab. Each function is compared with SciPy/statsmodels on 20 seeded
  datasets (largest difference 4.4e-16); Hypothesis checks properties (the CI contains the estimate, swapping arms flips
  the sign, Holm never lowers a p-value, …); and the Hillstrom numbers are recomputed from the CSV and compared with the
  lab's JSON to 1e-9 (difference 0.0).

### Why it is built this way (the design decisions)
- **Presigned POST over PUT:** only a POST policy can make S3 itself enforce a size range and an exact key.
- **202 + polling:** analyses can take seconds; HTTP requests should not. Workers scale separately from the API.
- **Idempotency key = sha256(file) + sha256(canonical mapping)** (+ abkit version): the same input never runs twice,
  and a shared link always shows the same numbers. The mapping is part of the key because the same file analyzed with
  a different metric or control is a different question.
- **Crash safety:** `acks_late` + `reject_on_worker_lost` mean RabbitMQ keeps the message until the task finishes. If a
  worker dies mid-job, the message is redelivered, and because the task is idempotent, running it twice is harmless.
  Only network/S3 hiccups are retried (2, 4, 8 s). Bad data fails at once with a code and a "what to fix" message.
  Soft time limit 120 s (recorded as TIMEOUT), hard 150 s.
- **abkit as its own package:** the statistics are versioned and tested on their own, and every analysis stores the
  abkit version and git commit that produced it.

### How it runs
- **Locally:** Docker Compose: Postgres, RabbitMQ, moto (fake S3), a one-shot migrate service, the API (gunicorn), the
  Celery worker, and nginx serving the built React app. One backend image (non-root, uv-locked venv) runs as both API
  and worker. Every base image is pinned by digest.
- **Kubernetes (Helm chart):** Deployments for web, api and worker (the worker has an HPA from 1 to 3 replicas at 70%
  CPU); StatefulSets with volumes for Postgres and RabbitMQ; a Traefik Ingress (`/api` → api, `/` → web) with a
  cert-manager TLS annotation; and the migration as a Helm hook Job. Readiness means "can serve" (DB and broker
  reachable); liveness means "process alive", so a broker outage does not cause restart loops. On k3d, a 20-job burst
  pushed worker CPU to 382% of its request, and the HPA went from 1 to 3 replicas.
- **Production plan:** one EC2 box running k3s. Pods reach S3 through the instance role via IMDSv2 (hop limit 2,
  because pods sit one network hop behind the host), so there are no AWS keys in the cluster. GitHub Actions builds
  images, SSHes in, creates the Kubernetes Secret from GitHub secrets, runs `helm upgrade`, and then a smoke test.

### Bugs found by actually running things (good interview stories)
1. **Statsmodels' `solve_power` is not precise enough for a 1e-4 check.** I proved the gap was in its root-finder
   rather than our formula, by solving statsmodels' own power curve to full precision. The formula stayed as it was. (D5)
2. **RabbitMQ 4.3 refused Celery's remote-control queues** (deprecated transient queues). The worker crash-looped,
   which unit tests in eager mode can never show. Fix: make those queues exclusive. (D9)
3. **DuckDB's CSV sniffer silently used a ragged row as the header.** Fix: declare the columns from the real header
   and turn auto-detection off, so a bad row becomes a clear BAD_CSV error. (D10)
4. **Helm rendered 52428800 as "5.24288e+07"** and crashed Django. Then a **pre-upgrade hook read the old ConfigMap**.
   Both were found on k3d. Fixes: `int64` plus a CI check of the rendered value, and a hook-owned ConfigMap. (D13)
5. **S3 returns 403, not 404, for a missing key when the role cannot ListBucket.** moto never shows this. Without the
   fix, production would have answered 500 instead of 409 and crashed the first deploy's seeding. (D14)
6. **A screenshot run caught a UX bug:** the form guessed "binary" for spend because the 20 preview rows were all 0.
   (D11)
7. **The HPA demo once showed no load:** identical burst files were matched by hash and reused. That was idempotency
   working, and it showed in a real measurement.

### Interview questions from SPEC section 15, short answers
1. *POST vs PUT:* the POST policy enforces `content-length-range` and the exact key, so S3 rejects oversize files.
2. *Worker dies mid-job:* `acks_late` + `reject_on_worker_lost` → the message returns to the queue → the idempotent task
   recomputes it (or finds the stored result).
3. *Why 202 + poll:* request timeouts, separate scaling of workers, and the UI stays responsive.
4. *Idempotency key:* sha256 of the bytes + sha256 of the sorted-key mapping JSON (+ abkit version); the mapping is
   included because the same file answers different questions under different mappings.
5. *Welch, not Student:* arms can have different variances (treatment changes behaviour); Welch costs nothing when they
   are equal. For 0/1 data at n ≈ 21,000 per arm the CLT makes the t interval accurate.
6. *SRM and p < 0.001:* it tests whether assignment worked. The strict threshold avoids false alarms across many
   tests. If it fires, stop and debug assignment and logging before reading any effect.
7. *CUPED on Hillstrom:* correlation with prior spend ≈ 0.07 → variance removed ≈ corr² ≈ 0.4%: no real gain.
8. *How you verified the statistics:* equivalence with SciPy/statsmodels, Hypothesis properties, and the lab
   reproduction to 1e-9 with values read from the lab's JSON.
9. *How the HPA scales:* average CPU vs 70% of the request, 1–3 replicas. Queue depth via KEDA would be a better signal.
10. *Pods reaching S3 without keys:* the EC2 instance role via IMDSv2 with hop limit 2.
11. *What Claude Code wrote and how you checked it:* the phase-by-phase log in PROGRESS.md, every judgement call in
    DECISIONS.md, tests and real runs at each phase, and an independent subagent review against "Done means" (below).
